# 主翼側風速計の生パルス記録・補正レポート

作成日: 2026-07-11

## 1. 目的

主翼側風速計2台の値を、生パルスカウントとして記録し、後からキャリブレーション式を適用して風速へ変換できるようにする。

比較対象は次の3系統である。

| 系統 | 送信元 | 記録する量 |
|---|---|---|
| メインビーム | `air_data` | `pulse_total`（0.5秒窓の総パルス数） |
| 左/第1主翼 | `wind_espnow`、device ID `0x03` | `wind_board_pulse`（0.5秒窓の総パルス数） |
| 右/第2主翼 | `wind_espnow`、device ID `0x04` | `wind2_pulse`（0.5秒窓の総パルス数） |

## 2. サンプリング期間と記録値

### 2.1 メインビーム側 (`air_data`)

- 50 msごと、20 Hzでパルス数を取得する。
- 10サンプルを加算して、0.5秒ごとの `pulseCountTotal` としてESP-NOW送信する。
- 従って `pulse_total` は**0.5秒間の生パルスカウント**である。

\[
C_{main}=\sum_{i=1}^{10} C_{50ms,i}
\]

### 2.2 主翼側 (`wind_espnow`)

- 500 ms周期のタイマーで、前回タイマー時点との差分パルス数を取得する。
- `sampleSlot.pulseCount` は**0.5秒間の生パルスカウント**である。

\[
C_{wing}=\text{pulse count during }0.5\text{ s}
\]

このため、同じ気流・同等のセンサー特性であれば、`pulse_total` と各 `wind*_pulse` は概ね同程度のオーダーとなる。

## 3. 判明した不整合

### 3.1 旧 `wind_espnow` は生パルスを送っていなかった

旧実装では、0.5秒カウントからPPSを計算し、さらに `windSpeedDeci` を送信していた。

\[
\mathrm{PPS}=\frac{C_{wing}}{0.5}=2C_{wing}
\]

旧コードの係数は `kWindSpeedPerPps = 1.0`、オフセットは `0.0` だったため、送信値は実質的に次の量となっていた。

\[
x=\mathrm{PPS}\times 10=20C_{wing}
\]

従って、旧データの `wind_board_pulse` は名前に反して生パルスではなく、概ね「PPS × 10」であった。

### 3.2 旧記録値を0.5秒生カウントへ補正する方法

旧記録値 $x$ はPPSの10倍である。一方、比較対象の `pulse_total` は0.5秒間の生カウント $C$ である。したがって、オーバーフローしていない旧記録値は次式で補正する。

\[
C=\frac{x}{10}\times0.5=\frac{x}{20}
\]

つまり、**旧 `wind_board_pulse` / `wind2_pulse` をメインビームの `pulse_total` と同じ「0.5秒生カウント」に揃えるには、値を20で割る。**

この補正には次の2段階が含まれる。

1. 10で割る: `PPS × 10` をPPSへ戻す。
2. 2で割る: PPSを0.5秒間のカウントへ戻す。

例として、旧記録値が $64000$ の場合は、PPSが $6400$、0.5秒生カウントが $3200$ となる。

\[
64000\div10=6400\ \mathrm{PPS}
\]

\[
6400\times0.5=3200\ \mathrm{pulses/0.5s}
\]

### 3.3 `uint16_t` のオーバーフロー

ESP-NOWパケットの `windSpeed` は `uint16_t` であり、取り得る範囲は 0～65535 である。

旧送信値がこの上限を超えると、値は65536を法として折り返す。

\[
x_{recorded}=(\mathrm{PPS}\times10)\bmod65536
\]

グラフに見られた「約65000まで増加した直後に0付近へ落ちる」挙動は、このオーバーフローの典型である。チャタリングのみでは、この規則的な折り返しは説明しにくい。

## 4. 実施した修正

`wind_espnow` は、送信フィールドへ `windSpeedDeci` ではなく、0.5秒窓の生カウント `sampleSlot.pulseCount` を格納するよう修正した。

```cpp
sendEspNow(static_cast<uint16_t>(sampleSlot.pulseCount));
```

この修正後は、主翼側の送信値が0.5秒間の生パルス数となる。

### 注意

この修正済みファームウェアは、**左右の主翼側風速計の双方**へ書き込む必要がある。片方だけ旧ファームウェアのままでは、値の単位が異なり比較できない。

## 5. 生データから風速を求める補正

主翼側のキャリブレーション式は以下である。

\[
W=\frac{P}{1237.6}+0.44
\]

ここで、$W$ は風速 [m/s]、$P$ はPPS [pulses/s] である。

保存する生カウントは0.5秒窓の値 $C$ であるため、PPSへは次式で変換する。

\[
P=2C
\]

従って、保存済みの修正後主翼データからの風速は次式で算出する。

\[
W=\frac{2C}{1237.6}+0.44
\]

### 可視化プログラム側の注意

可視化側で `pulse_to_wind()` に渡す値が0.5秒窓のカウントである場合、PPS換算の倍率2を必ず適用する必要がある。

```python
def pulse_to_wind(count_500ms: int) -> float:
    pps = count_500ms * 2.0
    return pps / 1237.6 + 0.44
```

`P / 1237.6 + 0.44` を直接適用すると、0.5秒カウントをPPSとして扱ってしまい、傾き成分が半分になる。

## 6. 旧オーバーフロー記録の復元

旧記録値 $x$ からの候補は次式で表される。

\[
\mathrm{PPS}=\frac{x+65536k}{10}
\]

\[
C_{wing}=\frac{x+65536k}{20}
\]

$k$ はオーバーフロー回数（0以上の整数）である。

すなわち、オーバーフローした旧値をメインビームの `pulse_total` と同じ0.5秒生カウントに補正する最終式は以下である。

\[
C_{corrected}=\frac{x_{recorded}+65536k}{20}
\]

オーバーフローがない区間では $k=0$ であり、単純に $x_{recorded}/20$ となる。

### 復元の可否

- 前後の時系列が連続的であること
- メインビーム側の風速または `pulse_total` と傾向比較できること
- 想定する最大風速が定まっていること

の条件があれば、$k$ を推定して実用的に復元できる。

ただし単独の記録値だけでは、例えば `3000` が「PPS 300」なのか「PPS 6853.6」なのかを一意に確定できない。このため、旧データの補正は推定を伴う。

## 7. チャタリングなど、残る誤差要因

オーバーフローを解消しても、左右の値に差が出る可能性はある。

| 要因 | 影響 | 確認・対策 |
|---|---|---|
| ファームウェアの不一致 | 生カウントと旧変換済み値が混在し、大きな差になる | 2台とも修正済みファームウェアを書き込む |
| センサー個体差 | 同一風速でもパルス周波数の係数が異なる | 左右別にキャリブレーション係数を求める |
| 磁石・センサー位置 | 磁石間隔、センサー距離、固定角度で検出数が変化する | 機械的取り付けを確認する |
| デバウンス | 短すぎるとノイズをパルスとして数え、長すぎると高周波パルスを落とす | 実機の最高回転数に基づき `kEncoderDebounceUs` を検証する |
| 主翼上の気流差 | ロール、ヨー、迎角、翼端渦、胴体の影響で左右の局所風速が異なる | 静的試験と飛行中データを区別して評価する |
| ESP-NOWの欠損・古い値 | 通信が止まった直後に直前値が見える可能性がある | 受信時刻による鮮度判定を維持し、タイムアウト時は0または欠損扱いにする |

## 8. 今後の確認手順

1. 左右の主翼側風速計へ、修正済み `wind_espnow` を書き込む。
2. ロガー出力の `wind=[pulse=...]` と `wind2=[pulse=...]` が、ともに0～およそ10000程度の0.5秒生カウントであることを確認する。
3. 一定風速の試験で、メインビームの `pulse_total` と両主翼のパルス値を比較する。
4. 可視化・解析では、主翼側生カウントを $W=2C/1237.6+0.44$ で風速へ変換する。
5. 左右差が継続する場合は、個別のキャリブレーション係数とオフセットを求める。

## 9. 結論

以前の主翼側グラフにあった大幅な変動と0付近への急落は、主に旧ファームウェアによる「PPS × 10」送信および `uint16_t` オーバーフローで説明できる。生パルスカウントを直接保存する方式に変更すれば、後から正しい係数で風速へ変換でき、キャリブレーションの再検討にも対応できる。
